## WHAT / WHY — accepted user outcome

An ordinary professional can **select a missed identifying fragment directly from the original document text**, choose/enter its type in human-facing Spanish, deliberately **Añadir dato marcado** or **Cancelar**, and immediately see the added entity as **pendiente de revisar** with a usable next action. **No source offsets, index numbers, ReviewSession or internal enum/type IDs are required as ordinary UI vocabulary**. Underlying ReviewSession still receives exact `{start,end,type}` source offsets; new manual detections remain `source:manual` and `requiresReview:true`, with no automatic `accepted`, `modified` or `restored` decision.

## CLOSED product/interactivity decisions — no writer design reopening

1. **Starting action:** Show a directly understandable Spanish affordance **“Marcar dato no detectado”** in/next to the original `DocumentPane`. Select a nonempty source span, then invoke the action. Do not introduce a global keyboard shortcut (owned by #83). All touched labels/help/errors in this interaction are Spanish-first. Existing highlighted detection buttons, decisions, preview and filters stay functional.
2. **Selection provenance:** Derive internal offsets **only** from the live/captured browser selection *within* the original document source-text group and its existing source-anchored DOM segments. Validate bounds, non-collapsed range, and exact `session.originalText.slice(start,end)` versus the selected original fragment before offering Add. Do **not** guess offsets with `indexOf`, rendered `innerText`, preview text, a global string search or arbitrary manual numeric fallback. Support legitimate selections across source-rendered segments when their exact source mapping is demonstrably valid; if the representation cannot prove fidelity, **refuse clearly**, do not silently narrow/map. Do not invent a new overlap classifier or change accepted ReviewSession overlap/composition semantics.
3. **Capture vs focus:** Capture the source-anchored selection at the explicit mark action, bound to the then-current immutable `ReviewSession` + source text. Browser loss/collapse of the *live* visual selection as focus moves to the inspector must **not** erase the already valid captured range. An empty/out-of-document/preview/cross-container/stale or otherwise unprovable selection **does not open an editable Add form, creates zero detections and shows a short Spanish recovery instruction near the trigger**.
4. **Marking panel:** Inline/contextual within the existing inspector, not a second Review page or detached dialog. Show **“Texto seleccionado”** containing exactly the captured source substring (a scrollable legible area for long selections, no hidden silent truncation), plus **“Tipo de dato”** (editable free text, nonempty). Keep type vocabulary **open**, not a forced closed dropdown replacing all possible manual types; known examples/help may be suggestions only. Provide `Cancelar` and an explicit `Añadir dato marcado` action; no source offsets appear as fields, labels, tooltip, placeholder, ordinary error or ordinary help. Do not double-log or persist PHI; display the selected synthetic/user-owned text only as the authorized in-memory Review UI.
5. **Confirmation / bridge:** Opening, choosing type, cancelling and failed validation are **zero ReviewSession mutations**. Add only on explicit submit and current range/session recheck; it creates exactly one new *pending* manual detection through the existing bridge. Existing detections' IDs, decisions and source text remain intact. Missing type, invalid range, domain refusal, context change and repeated clicks are fail-closed and actionable; preserve the selected span/type on a same-context validation error so it can be corrected without reselecting.
6. **Post-action continuation:** On Cancel, close the panel without changing selection/decisions/filters or the user's previously selected detected entity; put keyboard focus back on the source marking affordance (browser highlight may naturally collapse). On valid Add, close/reset the draft, show a Spanish factual **“Dato añadido. Pendiente de revisar”** confirmation and an explicit **“Revisar dato marcado”** next action addressing the *newly created* pending entity in the inspector/list. Do not silently decide it, silently reset a user-chosen filter, jump to Gate, or clear unrelated reviewer notes. If the current filter hides the new item, the next-action affordance remains discoverable and focuses/selects it intentionally, without changing other accepted decisions. A subsequent ordinary `Modificar` decision/return to Result must still work.
7. **Context invalidation:** Switching current ReviewSession (new Job, batch active document, structured free-text cell, reprocess) must revoke **all captured selection/marking authorizations** before any Add. Reused positions, text or detection IDs never authorize a stale submit. A same-session failed operation may retry; an unrelated session revision must not allow an old numeric span to be silently replayed. Never transfer marking state across consumers/unmount.
8. **Spatial consequence and focus:** A mark made from the document must bring the inspector's marking panel **into the viewport** and focus an appropriate editable control, including mobile. Its text, type and Cancel/Add controls must remain keyboard-reachable at 375 px and 1280 px with no horizontal overflow; after Cancel/Add, the next action is visible/reachable. The #82 mobile `Volver a detecciones`, confirmation controls and focus route survive untouched. Do not redesign the overall 3-pane Review or a global navigation shell (#83/#84 own wider interaction changes).
